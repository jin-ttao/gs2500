# GS2500 — 다점포 동시 진열 실험실

9개 합성 점포 × 진열 후보 4개, 총 36개 세계를 함께 실행하는 로컬 3D 데모다.
데스크톱 한 페이지에는 점포 4곳 × 후보 4개, 최대 16개의 실시간 3D 카드를 표시한다.
Blender 리깅 모델과 생성된 상품 포장을 사용한다. 실제 GS / Nemotron / JEV와 연결하지 않는다.

## 실행

```bash
cd demo
npm ci
npm start
```

http://127.0.0.1:4173 에서 연다. 설치 후에는 외부 CDN이나 API 키가 필요 없다.
`npm test`로 데이터·공간·동시 실행·결제 동기화 테스트를 실행한다.
`npm run test:day`는 명시적인 `everyday` 그룹의 3점포 × 4안 = 12개 세계에서
점포당 잠재 고객 1,000명의 24시간을 끝까지 실행해 시계·재고 보존·결제 원장·시간별 집계를 검사한다.
검사 시간 제한을 위해 900×를 사용하며, 기본 보드의 36개 전체 세계 검사나 브라우저 속도 측정은 아니다.
Node.js 22 이상, npm, Python 3, WebGL 지원 브라우저가 필요하다.
`npm run build`는 정적 배포용 파일을 `dist`에 만들고, `npm run preview`는 이를
`http://127.0.0.1:4174`에서 확인한다. 빌드는 외부 배포를 실행하지 않는다.

## 체험

1. 전체 실행을 시작하면 삼성역점(합성 오피스형), 역세권·주거지·한강변·대학가·관광지·골목·카페·공원
   데모점의 본사 표준 / 재고 우선 / 균형 후보 / 신상품 탐색안, 총 36개가 함께 진행된다.
2. **각 카드 자체가 실시간 3D 시뮬레이션 화면**이다. 데스크톱은 점포 4곳을 2×2,
   각 점포의 후보 4개도 2×2로 배치해 한 페이지에서 최대 16개를 비교한다.
   전체 점포는 4곳 / 4곳 / 1곳의 세 페이지다. 터치·트랙패드의 좌우 스와이프,
   마우스 드래그, 이전·다음 버튼과 페이지 점으로 이동하며, 페이지 이동은 실험을 초기화하지 않는다.
   모바일에서는 후보 4개의 2×2 배치를 유지하고 같은 페이지의 점포 묶음을 세로로 쌓는다.
   각 점포·후보의 실제 고객이
   걷고, 상품을 살펴보고, 집고, 결제한다. 아래 지표는 그 세계의 결제와 퇴장 결과다.
   카드를 누르면 상세 3D 관찰 창이 열리고, 닫기나 Escape로 비교 보드에 돌아온다.
   관찰 창을 여닫아도 다른 실험은 계속 진행되며 초기화하지 않는다.
3. 하루는 00:00–24:00이다. 점포당 잠재 고객 1,000명이 시간대별로 지나가며
   필요·영업 시간·혼잡에 따라 입장하거나 지나친다. 전원 강제 방문이 아니다.
   UI의 1 / 4 / 16 / 32 / 128 / 900배속은 입장·이동·탐색·집기·결제·보충·퇴장에
   함께 적용된다. 기본 4배속으로 동작을 천천히 관찰한다. 카드 모션만 따로 늦추지 않는다.
4. 일시 정지는 36개 세계와 지표·캐릭터 포즈를 함께 멈춘다. 카메라 조작은 가능하다.
   탭이 백그라운드로 전환되어도 정지하며, 복귀 후 재개 버튼으로 이어서 실행한다.
5. 초기화는 모든 방문·재고·결과를 초기 상태로 돌린다. 선택한 후보와 배율은 유지된다.

## 동기화 구조

기존 UI의 독립적인 `createExperiment / visit` 배치 실행을 제거했다.

- `lab.js` 한 곳만 시간을 전진시킨다. 0.05초 고정 간격마다 미완료 후보 36개를
  모두 업데이트한 다음 브라우저에 렌더링 시간을 돌려준다. 모든 점포가 비어 있고
  보충 작업도 없으면 다음 실제 예약 사건까지만 함께 건너뛴다. 행동은 생략하지 않는다.
- `world.js`가 실제 이동·상품 비교·집기·매대 차감·대기열·결제·퇴장과
  점주의 창고→매대 보충 작업을 계산한다.
- `store.js`는 선택된 **같은 world 객체**의 위치·상태·재고를 그린다.
  자체 세계, 별도 방문 루프, 26초 예열, 별도 실시간 시계가 없다.
- `card-worlds.js`는 하나의 WebGL 렌더러를 현재 보이는 카드 영역으로 나누어 그린다.
  각 카드가 `lab.runs`의 현재 world를 참조하므로 초기화 후에도 이전 세계를 보여주지 않는다.
  카드용 가구는 인스턴싱한 간소화 모델이며 지도 좌표와 진열안은 상세 보기와 같다.
  고객은 상세 보기와 같은 Blender 스킨·모션을 사용한다. 다른 페이지나 모바일에서 보이지 않는 카드는
  그리기만 생략하고 시뮬레이션 계산은 계속한다. 다시 보이면 현재 상태의 포즈를 그린다.
  카드의 상품 포장은 공유 진열 좌표마다 한 페이싱을 표현하며 재고 개수와 비례하지 않는다.
  실제 수량은 숫자로 표시하며, 재고가 0이면 해당 상품의 포장은 모두 숨긴다.
- 스켈레톤·걷기·팔 동작·회전·계산원 애니메이션은 해당 world의 실제 시간 변화량을 사용한다.
- 카드 지표와 이벤트 로그도 같은 world.snapshot()에서 읽는다. 물건을 담는 순간에는
  재고만 차감되고, 결제 동작이 완료된 실제 이벤트에서 매출이 증가한다.
- 렌더러 snapshot의 renderedTime / renderedRunId는 실제 그린 시점과 실행 ID다.
  UI의 syncProbe는 지표와 3D가 동일 실행·시간·좌표를 읽었는지 확인하기 위한 DOM 검사값이다.
  `cardViews.cards`는 각 카드가 실제로 그린 시각·실행 ID·고객 좌표를 기록한다.
  `visible:false`인 화면의 마지막 그린 값은 현재 엔진 값으로 위장하지 않는다.

배속은 요청한 속도다. 기기 성능이 부족하면 계산 예산으로 전체 세계를 함께 늦추고
실효 배속·밀린 시간을 표시한다. 숫자나 3D 중 하나만 앞서 진행하지 않는다.
일시 정지나 배속 변경 시 아직 계산하지 않은 벽시계 잔여 시간은 버려 지연된 고배속이
사용자 조작 후 계속 실행되지 않게 한다. 이미 계산된 사건이나 지표는 되돌리지 않는다.

고배속에서는 한 렌더 프레임 사이에 짧은 행동 여러 개가 끝날 수 있다.
이때 현재 상태만 화면에 보이지만 모든 행동은 엔진에서 순서대로 계산된다.
경과 시계는 실제 엔진 초 단위다. 기본 4배속의 산술상 24시간은 6시간이다.
빠른 하루 비교용 900배속은 산술상 96초지만 실제 실행 시간은 연산·그리기 성능에 따라 더 길다.
UI에 표시되는 실효 배속이 기준이며, 4배속에서 몇 분 안에 하루가 끝난다고 보장하지 않는다.

## 하루의 경계와 재고 보충

실험 종료 조건은 재고 소진이나 방문 1,000회 완료가 아니라 **24:00 도달**이다.
잠재 고객 1,000명의 평가가 그 안에 모두 끝나도록 시드 기반 일정을 만든다.
기본 영업 시간은 24시간이며, 시간대별 가중치·입점 의향·가상 이벤트는 검증되지 않은 가정이다.
매출은 계산대에서 결제를 마친 순간에만 기록한다. 24:00까지 결제하지 못한 바구니는
창고로 반환하고 매출에 넣지 않으며, 일 종료 후 추가 결제나 보충도 발생하지 않는다.

상품별 `initialTotalStock = shelfStock + backroomStock`으로 시작한다.
매대 용량은 상품별 8~18개의 합성 설정이다. 보충 직원은 저재고 상품을 골라
창고 서비스 지점에서 매대 서비스 지점으로 A* 경로를 따라 이동한 다음 진열한다.
이동 속도 기본 1.1m/s, 상품별 서비스 시간 기본 6초, 보충 기준 기본 용량의 35%이다.
진열이 끝난 시점에 `min(창고 재고, 남은 매대 용량)`만 옮긴다.
창고까지 바닥나면 더 채울 수 없다. 외부 발주·배송·자동 재입고는 구현하지 않는다.
계산원과 보충 담당자는 별개인 **2개 역할 가정**이며, 실제 점주 1인의 업무 경합을 재현하지 않는다.
같은 SKU의 진열 재고는 매장 공용 수량으로 단순화했고, 보충 동작은 행사 매대 서비스 지점에서
표현한다. 각 선반 위치마다 별도 재고나 보충 직원-고객 간 충돌 회피까지 모델링하지는 않는다.

초기 수량 = 매대 + 창고 + 아직 결제하지 않은 바구니 + 결제된 수량이다.
매대 품절로 놓친 수요와 창고까지 소진된 품절을 구분한다.
상세 화면의 하루 분석은 시간대별 유입·입장·구매·매출과 보충 기록을 보여준다.
기록 JSON 내보내기는 이 실행의 전체 사건을 보존하며 실제 고객 데이터가 아니다.

## 계산과 가정

현재 상품은 직접 작성한 가상 SKU 24개, 페르소나 유형은 5개다.
각 점포에 고유한 잠재 고객 1,000명의 일정을 만든다. 퇴장한 ID를 반복 경로에 재사용하지 않는다.
동시 고객 상한은 오피스·주거지 14명, 역세권 10명이다.

점포별 서로 다른 고정 시드·페르소나 가중치·재고 배율을 사용한다.
같은 점포의 네 후보는 초기 총재고와 잠재 고객 일정·특성·입장 의향 난수를 공유한다.
후보가 만드는 혼잡·체류 시간 차이로 입장 거절이나 구매 결과는 달라질 수 있다.
A/B/C/D는 같은 1,000명에 대한 반사실 비교다. 카드별 사람 수를 독립 고객처럼 합하지 않는다.
신상품 탐색안(D)은 합성 신상품 5종을 2층에 모으고 함께 고를 상품을 3층에 둔 별도 4×6 배치다.
모든 후보는 같은 가상 상품 24개를 정확히 한 번씩 사용하며 신상품 후보에 별도 승률 보너스를 주지 않는다.

- **잠재 고객 평가**: 해당 시간까지 입장 또는 지나침이 확정된 사람 수.
- **입장 / 지나침**: 필요 없음·영업 종료·혼잡 등 입장 여부의 결과. 강제 대기 후 재시도하지 않는다.
- **방문 완료**: 출구에 도달한 고객 수. 결정 수, 입장 수, 결제 수와 다르다.
- **누적 모의 매출**: 결제가 완료된 상품 가격의 합계. 실제 POS 실적이나 미래 예측이 아니다.
- **누적 매출총이익**: 실제 결제액 - 판매된 상품의 합성 매입원가.
  원가율은 식사 71%, 음료 64%, 과자 62%, 건강식 68%를 10원 단위로 반올림한 가정이다.
  임대료·인건비·세금·프로모션 할인·폐기 비용은 포함하지 않는다.
- **미충족 구매 시도 비율**: 품절로 실패한 구매 시도 / 전체 구매 의향 발생 수.
  같은 사람이 다른 코너에서 다시 시도할 수도 있으므로 잃은 고객 수나 통계적 결품 확률이 아니다.
- **판단 수**: 실제 진열 앞에 도착한 뒤 인지한 상품을 비교한 횟수.
- **층별 지표**: 행사 매대에 실제 도착한 고객의 노출·인지·집기. 다른 코너의 선택은 포함하지 않는다.

행사 매대 층별 기본 인지 확률은 미검증 가정이며 정확한 좌표·주변 상품·혼잡·신상품·이벤트
맥락도 로컬 판단 입력에 포함된다. 그 맥락이 실제 JEV 호출로 전달되는 것은 아직 아니다.
이 위치 효과는 실제 상품 선택과 재고 차감에 반영되며 단순한 팔 동작 변경만이 아니다.
매대 재고 0인 상품은 바로 집을 수 없고 3D 상품 모델도 숨겨진다. 창고에 재고가 있으면
보충을 마친 뒤 다시 나타난다. 수량은 음수가 되지 않는다.

같은 초기 재고가 하루 안에 모두 팔리면 후보별 최종 매출이 같을 수 있다.
강제로 우승 후보나 상승률을 만들지 않는다. 시점별 매출·체류·품절 실패 등은 달라질 수 있다.
완료 전 진행 중 매출만으로 성과 순위를 확정하지 않는다. 승인 가능 시점도 24시간 종료 후다.

## 파일

- `lab.js`: 점포 설정, 기본 전체 9점포 × 4안 = 36개 실행, 단일 고정 간격 시계·배속·정지·진행 관리.
  명시적인 `everyday` / `destination` / `neighborhood` 그룹도 지원한다(각 3점포 × 4안).
- `world.js`: 고객 목적·공간 행동·상품 선택·재고·결제·이벤트
- `day.js`: 시간대별 잠재 고객 일정, 입장 의향 가정, 초기 매대·창고 분리
- `store.js`: 선택한 world를 그리는 3D 렌더러, 카메라·고객 선택
- `card-worlds.js`: 보이는 카드의 공유 WebGL 렌더러와 점포별 3D 장면
- `components/ui/store-pager.js`, `store-pages.css`: 4점포 단위 페이지, 네이티브 터치 스크롤·스냅,
  마우스 드래그·버튼·점·방향키 이동과 데스크톱 16카드 / 모바일 점포별 2×2 배치.

## 범위와 한계

시드 기반 로컬 규칙 시뮬레이션이며 실제 GS 추천·JEV 호출·Smallville 기억 검색/반성은 없다.
3D 캐릭터는 19개 본과 8개 모션을 가진 원본 모델이지만 실사 스캔·전신 IK는 아니다.
매장 도면은 가상이며 카페 테이블은 정적 장애물이다.

현재 개선 범위는 **실제로 동기화된 36개 공간 시뮬레이션과 페이지당 최대 16개 화면 비교**다.
앞서 작성한 제출용 목표 전체(20개 상품, 지난주 데이터 분석, 실제 인증·서버 승인,
실제 수요로 보정한 24시간 예측, GitHub/Vercel 배포, 신상품 추천)를 완료했다고 주장하지 않는다.
구현된 승인 기능은 같은 브라우저의 localStorage에 저장하며 실제 접근 제어가 아니다.
