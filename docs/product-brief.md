# GS2500 제품 맥락

2026-09-22 기준 제품 방향입니다. 구현 화면과 발표 동선은 [3분 콘티 HTML](../design/reference/gs2500-storyboard-handoff.html), 작업 운영안은 [단일 `/goal` 프롬프트 초안](../goal-prompt.md)을 함께 참고합니다. 3D 입력·출력 계약은 실제 동료 코드 확인 후 확정합니다.

## 풀려는 문제

GS25 본사는 표준 진열 지침을 주지만, 가맹점마다 취급 상품과 현재 재고가 달라 그대로 실행하기 어렵습니다. 점주는 매출을 높이고 싶지만 어떤 진열을 바꿔야 할지 모릅니다. 본사와 가맹점 사이의 영업관리 매니저는 여러 점포의 실적을 보고 실질적인 매출 개선 팁과 지원을 제공해야 합니다.

본사 관점에서는 한 점포의 성공담만으로 부족합니다. 가맹점 전체에서 실행 부담을 낮추고, 전년 동기 대비 매출 신장에 기여할 수 있는지, 성과가 나지 않는 점포를 어떻게 다시 지원하는지까지 보여줘야 합니다. 본사가 일방적으로 지시하고 점주에게 일이 늘어나는 경험이 아니라, 점주도 납득할 이유와 적은 실행 부담을 얻는 관계를 지향합니다.

## 두 사람의 핵심 일

- 매니저: 담당 점포의 전년 동기 대비 매출에서 출발해 개입할 매대를 고르고, 여러 점포의 진열 후보와 시뮬레이션 결과를 비교한 뒤 가맹점에 보낼 제안을 승인합니다. 본사 지침은 후보를 만드는 참고 자료입니다.
- 점주: 본인 점포에 도착한 이번 주 진열 제안과 근거를 보고 수용하거나 일부 바꿉니다. 실제 진열을 사진으로 남기고 필요할 때만 의견을 보냅니다. 이후 판매·재고 추적과 분석은 에이전트가 맡는 경험을 지향합니다.

점주가 여러 후보의 계산을 다시 수행하거나 다른 점포의 성과를 분석하도록 요구하지 않습니다. 복잡한 비교는 매니저 화면에서 끝냅니다.

## 매니저의 주요 경험 3가지

1. **가맹점 성과 분석:** 여러 담당 점포 중 어디에 개입할지, 지난주 무엇이 기대와 달랐는지 이해합니다.
2. **시뮬레이션 과정과 결과:** 점포별 후보가 만들어지는 과정을 보고, 예상 결과와 근거를 비교하며, 필요할 때 3D 매장 행동을 확인합니다.
3. **진열 제안:** 선택한 안의 이유와 조건을 확인하고 승인해 해당 점주에게 보냅니다.

대화 입력은 성과 분석을 시작하는 방식입니다. 병렬 에이전트 연출과 3D 화면은 시뮬레이션을 이해시키는 방식입니다. 승인 버튼은 진열 제안의 마지막 결정입니다. 이들을 별도의 주요 경험으로 늘리지 않습니다.

## 데모에서 보여줄 순서

매니저 홈의 점포별 전년 동기비 → 개입할 매대와 후보·근거 → 여러 점포의 여러 옵션을 함께 보는 30일 시뮬레이션 전광판 → 후보 상세와 3D 행동 → 매니저 승인·수정 가능한 점주 안내 문자 초안 → 점주 PC 화면의 현재 진열 사진 한 장·선반 이동 도식·추천 이유 → 점주의 수용·부분 실행·거절과 사진·의견 접수 → 4주 후 합성된 좋은·부진·미회신 사례를 매니저가 회고하고 본사의 다음 지원과 지침 판단을 돕는 흐름입니다. 발표 경로는 3분을 목표로 합니다. 후보 수와 점포 수는 콘티의 예시에 묶지 않습니다.

추천 근거의 예시는 인기 상품, 더 잘 드러나야 하는 상품, 다른 점포의 성과, SNS 신호, 할인, 신상품입니다. 새로 발주하면 좋을 상품이 후보에 포함될 수 있지만 실제 발주 실행은 아직 확정되지 않았습니다.

## 작업 경계

- 타오: 3D 시뮬레이션을 제외한 매니저·점주 웹앱, 승인·사진 접수·회고 흐름, 공개 URL에서의 연결과 전체 검증.
- 유찬님: `codex/multi-store-live-3d` 브랜치의 다점포·다후보 3D 시뮬레이션 전광판과 후보 상세. 이 부분의 개발 목표와 실행은 유찬님이 별도로 맡습니다.
- 웹앱과 3D의 입력·출력 계약은 실제 산출물을 확인한 뒤 정합니다. 서로의 UI와 기능을 덮어쓰지 않고 공통 합성 fixture 또는 어댑터로 연결합니다.

### `/goal` 메인 작업 운영 결정

메인 Codex `/goal` 작업 한 개를 웹앱 개발의 허브로 운영합니다. 이 메인 작업이 작업 분해와 우선순위, 하위 작업의 파일 소유권, 결과 통합, E2E 검증, 기존 공개 저장소·배포 업데이트, 제출용 메인 JSONL을 책임집니다. 경계가 독립적인 구현만 내부 하위 에이전트에 위임하며 서로 같은 파일을 동시에 수정하지 않습니다. CEO 타오는 제품 방향과 필요한 승인 결정을 맡고, 유찬님의 3D 시뮬레이션은 별도 작업으로 유지합니다. 독립 검증은 메인 구현과 컨텍스트가 분리된 읽기 전용 검사로 진행합니다. 이는 이전 핸드오프의 `타오가 허브`라는 운영안을 갱신한 결정이며, 새 메인 `/goal` 원문에 포함해야 합니다.

## 진실성 및 데모 경계

- 판매, 재고, 진열, 본사 지침, SNS 신호는 확보된 실제 GS25 데이터가 아니라 합성 데모 데이터로 구성합니다.
- `GS25 점포경영시스템`은 데모의 진입 맥락입니다. 실제 사내 시스템과 연동하거나 그 화면을 정확히 복제했다고 주장하지 않습니다.
- 에이전트의 병렬 분석, 사진 이해, 이후 자동 추적 중 무엇이 실제로 동작하고 무엇이 사전 구성된 데모인지는 화면과 발표에서 구분해야 합니다.
- 시뮬레이션 결과는 가정 기반 예상이지 검증된 매출 상승이 아닙니다.
- 한 달 뒤 성과 사례도 합성 데이터로 만든 시연입니다. 좋은 사례와 부진한 사례를 함께 보여주되, 인과적으로 이 제품 덕분에 매출이 올랐다고 주장하지 않습니다.
- 전년 동기 대비 매출 신장은 핵심 관찰 지표입니다. 단일 점포 수치와 비교 가능한 점포들의 전체 추세를 구분하고, 채택 여부·결품·행사 등의 다른 설명 가능성을 함께 보여줍니다.
- 회고 화면은 제안 매대, 매니저 승인, 점주 회신·사진 접수의 분모를 구분합니다. 사진 접수만으로 실제 진열 변경을 검증했다고 말하지 않습니다. 좋은 사례뿐 아니라 수정·거절·부진·미회신 사례와 이유도 포함합니다. 단순 총매출 증감은 점포 수 변화가 섞일 수 있으므로 비교 가능한 점포의 전년 동기 대비 매출을 별도로 표시합니다.
- 본사의 다음 결정은 진열 지침을 확대, 수정, 보류하는 선택입니다. 점주에게는 이유가 납득되는 작은 행동 하나를 제안하고, 수용하지 않을 자유와 그 이유를 남길 경로를 둡니다.
- 화면은 데스크톱 전용으로 설계합니다. 점주의 사진은 데스크톱에서 파일 업로드로 시연하며 모바일 UI는 이번 데모 범위에 포함하지 않습니다.
- 최종 결과물은 외부에서 열리는 Vercel URL에서 핵심 경로가 실제로 동작해야 합니다.
- 별도 DB나 외부 저장 서비스 없이 합성 데이터로 작동하는 프로덕션 배포 데모입니다. 승인·메모·사진 접수 상태는 같은 브라우저의 시연 흐름에서 이어지게 하되, 실제 점주 기기와 데이터가 공유되거나 사진이 서버에 영구 저장된다고 주장하지 않습니다. 사진 파일의 유지 범위는 구현과 화면 안내가 일치해야 합니다.

GS리테일의 [상생경영 안내](https://hpimg.gsretail.com/gsretail/ko/esg/win-win)는 GS25 경영주 운영 지원과 현장 제안을 정책 개선에 반영하는 통로를 소개합니다. 이는 본사와 점주의 상호 이익을 설명하는 공식 맥락일 뿐, 이 데모가 해당 제도나 실제 시스템과 연결됐다는 뜻은 아닙니다.

## 구현 시 확인할 것

- 유찬님 브랜치의 최신 코드에서 실행법, 점포·매대·후보 입력, 현재 진열 기준선과 30일 결과 출력 형태를 확인합니다. 3D 화면 내부를 재구현하지 않습니다.
- 웹앱과 시뮬레이션의 점포·매대·SKU·재고·선반 위치·후보 ID·예측값을 재현 가능한 공통 합성 시나리오로 맞춥니다. 전년 동기비 실적, 30일 예상치, 4주 후 합성 관찰치는 서로 다른 시점과 의미로 표시합니다.
- 점주의 `일부 바꾸기`는 실제 매장에서 하는 행동입니다. PC 앱은 현재 사진에 이동 위치를 표시하고, 이후 사진 파일과 선택적 메모만 접수합니다. 진열안 편집기나 이미지 자동 판독은 만들지 않습니다.
- 공개 URL에서 매니저 승인 → 점주 화면 → 사진 접수 → 4주 후 회고를 E2E로 확인합니다. 실제 AI 실행과 사전 구성된 연출은 구분합니다.
