# GS2500 · 심사 기준별 근거

## 2. `/goal`의 구조와 현재 결과

### 보존 원문의 기본 구성

| 구성 요소 | 원문이 정의한 결과·경계 | 현재 확인할 결과 |
| --- | --- | --- |
| 문제·사용자 | 표준 진열과 점포 현실의 차이. 점주에게 근거 없는 일을 추가하지 않기 | 점포 선택, 매대 진단, 보유 재고·작업 부담을 고려한 후보 |
| 완료 상태 | 실적→비교→승인→점주 도면→회신·사진→적용 이후 검토 | [실제 화면 15장](screenshots/)과 연결된 로컬 업무 흐름 |
| 확인 기준 | 동일 조건 비교, 미승인 비노출, 정확한 승인안 전달, 나쁜 결과도 표시 | 계산·상태 검사, 점주 역할 브라우저 확인, 부진 사례 포함 |
| 제약 | 실데이터·실주문·실문자·검증된 매출 상승으로 표현하지 않기 | 합성 데이터 표시, 로컬 규칙, 메시지 초안, 실행 경계 설명 |
| 판단 범위 | UI 세부는 위임, 유료·실데이터·삭제·목표 변경은 승인 필요 | 사용자 피드백 반영, 유료 모델 연동과 제품 UX 개발 분리 |
| 허브 책임 | 독립 작업의 소유권, 기존 3D 보존, 계약·통합·테스트·결과 정리 | 하위 작업별 역할과 공통 계약, 기존 엔진 테스트 유지 |
| 검증·종료 | 성공 경로 외에 사진 실패·새로고침·3D 실패 확인, 한계 보고 | [검증 기록](../workspace/VERIFICATION.md), 현재 범위 명시 |

### 목표의 변경을 숨기지 않는 방법

원문은 과거 시점의 계약으로 보존합니다. 현재 구현을 설명하기 위해 원문에 있던 “24시간”을 “30일”로 소급 변경하지 않았습니다.

| 원문 또는 초기 상태 | 후속 요청·결정 | 현재 구현과 한계 |
| --- | --- | --- |
| 기존 24시간 3D 엔진 사용 | 0원부터 빠르게 30일 매출을 비교하고 싶다는 요청 | 별도 30일 수요·재고 모형 추가, 수치와 대표 3D가 같은 기록 사용. 기존 `demo/`는 24시간 유지 |
| 공개 Vercel URL | 사용자가 우선 로컬호스트 진행을 선택 | 본 문서의 검증 대상은 4175 로컬 앱. 최신 공개 배포 완료를 주장하지 않음 |
| 4주 후 합성 회고 | 이미 2주·4주가 지난 제안을 추적하는 화면 요청 | 14/28일 적용 이력 4건과 신규 승인·회신을 분리 |
| 기존 실험실의 로컬 저장 언급 | 새 통합 흐름에서 사진·승인 상태를 명시적으로 관리 | 루트 앱은 탭 메모리. 새로고침 시 초기화하며 영구 저장으로 표현하지 않음 |
| JEV 연결 실험 | 사용자가 JEV는 뒤로 미루고 UX·UI 완성을 우선 | 현재 루트 계산은 로컬 규칙. 과거 연결 실험을 현재 런타임 호출로 제시하지 않음 |

**실제 입력 증거의 경계:** 팀은 다른 컴퓨터에서도 `/goal`을 실행했다고 설명했습니다. 이 문서 작성 시 해당 기기의 주요 JSONL을 대조하지 않았으므로, 그 실행의 모델·시간·토큰·완료 상태는 아래 집계에 추가하지 않았습니다. 저장소의 `goal-prompt.md`는 내용 보존본이며 실행 증명은 아닙니다. 제출할 주요 JSONL에서는 사용자 입력 또는 `create_goal` 호출과 이후 결과를 함께 확인해야 합니다.

원문에 포함된 공개 배포·영상·발표 자료 등 제출 준비 전체가 현재 로컬 기능 검증으로 충족된 것은 아닙니다. 이 문서와 세션 증거는 제품 구현의 근거이며 제출물별 확인을 대체하지 않습니다.

## 3. 결과 중심 라우팅과 모델 활용

작업명은 세션 호출에서, 구현 결과는 저장소에서 확인했습니다. 이 표는 각 파일의 모든 줄을 특정 에이전트가 단독 작성했다는 의미가 아닙니다. 허브가 수정·통합하고, 같은 문제를 다른 검증 작업이 다시 확인하는 방식입니다.

### 왜 GPT-6 Astra에 이런 작업을 맡겼는가

[공식 가이드](https://developers.openai.com/api/docs/guides/latest-model)는 GPT-6 Astra의 코드·브라우저를 넘나드는 다단계 작업과 변경된 요구를 반영하는 특성을 설명합니다. GS2500에서는 그 특성에 맞춰 다음과 같은 연결 작업에 활용했습니다.

| 필요한 판단 | 맡긴 작업 | 산출물·검증 |
| --- | --- | --- |
| 기존 엔진을 보존하며 새 제품을 완성 | 업무 화면과 독립 3D 실험실의 계약·어댑터 통합 | 두 실행 경로 분리, 기존 테스트 유지 |
| 숫자·시간·화면의 불일치를 함께 진단 | 별도 관찰 엔진을 공유 계산 기록의 대표 재생으로 교체 | 배속·탐색에 따른 최종 매출 불변, 같은 SKU·구매 기록 사용 |
| 요구 변경 중에도 업무 맥락 유지 | 운영 화면·이력 화면·승인·스크롤 보존을 함께 점검 | 후보 왕복, 필터·입력·재생 상태 복원 |
| 독립적으로 검증할 수 있는 부분 병렬화 | 데이터·UI·이력·회귀 검사를 하위 작업에 위임 | 허브 통합 후 자동 검사와 브라우저 재검사 |

로그에서 `gpt-5.6-sol`과 `gpt-6-astra` 모델 컨텍스트를 확인했습니다. 위임 호출은 Astra 컨텍스트 구간에서 확인되며, 이것을 자동 모델 선택 정책이나 비용 최적화 벤치마크로 해석하지 않습니다. 개발용 Codex 모델과 제품의 로컬 시뮬레이션 엔진은 별개입니다.

## 4. Codex 활용 규모 — 고정 시점, 한 세션만

집계 기준 시각은 **2026-09-22 11:37:00 KST / 02:37:00 UTC**입니다. GS 개발에 연결된 로컬 허브 세션 1개만 읽어 집계했습니다. 다른 기기의 `/goal` 작업, 별도 포크, 자식 세션의 사용량은 합산하지 않았으며, 이후 README 정리 작업도 포함하지 않습니다.

| 항목 | 확인된 값 | 정의 |
| --- | ---: | --- |
| 응답별 사용량 기록 | 1,510건 | 고유 `response_id`가 있는 `token_usage_record` |
| 입력 토큰 | 217,448,426 | 응답별 `usage.input_tokens` 합계, 반복 입력 문맥 포함 |
| 캐시 입력 토큰 | 211,032,704 | **입력 토큰에 포함된 부분집합** |
| 출력 토큰 | 775,897 | 응답별 `usage.output_tokens` 합계 |
| 추론 출력 토큰 | 172,801 | **출력 토큰에 포함된 부분집합** |
| 입력 + 출력 | 218,224,323 | 캐시·추론을 다시 더하지 않음 |
| 완료 턴 | 57개 | `task_complete` 이벤트 |
| 완료 턴 기록 시간 합계 | 9시간 7분 55.952초 | `duration_ms` 합계 32,875,952ms. 도구 대기 포함 |
| 하위 작업 생성 호출 | 32회 | `spawn_agent` 호출 횟수. 재시도를 포함하므로 성공한 에이전트 32명을 뜻하지 않음 |

### 집계 방법과 오해하기 쉬운 점

1. 지정한 JSONL을 읽기 전용으로 순회하고 기준 시각까지의 레코드만 선택했습니다. 원본을 변환하거나 공개 저장소에 복사하지 않았습니다.
2. 응답별 `usage`만 `response_id`로 중복 제거해 합산했습니다. 누적값인 `turn_token_usage`·`thread_token_usage`를 다시 더하지 않았습니다. 선택된 1,510건에 누락·중복 response ID는 없었습니다.
3. 입력에 캐시를, 출력에 추론을 포함하므로 네 항목을 전부 합치지 않습니다. 입력 토큰은 고유 문서량·학습량이 아니며 큰 문맥을 반복 읽은 사용량입니다.
4. 1,510건은 사용자 요청 수, 유료 API 청구 건수, JEV 호출 수가 아닙니다. 도구 호출 횟수와도 다릅니다. 실제 청구 금액은 계산하지 않았습니다.
5. 완료 시간은 순수 모델 추론 시간이 아닙니다. 중단·진행 중 턴과 다른 기기의 시간은 제외하며 전체 프로젝트 인력 시간으로 해석하지 않습니다.
6. 세션은 계속 커질 수 있으므로 **위 기준 시각까지의 집계**만 고정합니다. 이는 종료된 제출용 로그의 안정된 스냅샷·해시 검증을 대신하지 않습니다.

## 6. 비즈니스 실증과 제출 증거의 다음 단계

**파일럿의 성공 기준:** 영업관리자의 검토 시간과 점주의 실행 부담을 먼저 측정하고, 동일 기간·대조 조건에서 대상 SKU의 매출총이익·품절·재고 소진을 함께 평가합니다. 가격·행사·입고·부분 실행을 기록해 개선이 진열 때문인지 검토합니다. 합성 결과는 이 평가를 준비하는 도구이지 성과 증명이 아닙니다.

**실행 로그 제출:** 다른 기기에서 실행한 주요 `/goal` 세션을 정한 뒤 실제 입력 또는 `create_goal`, 결과, 검증·종료를 함께 대조해야 합니다. 원본 대화에는 API 키·개인정보가 포함될 수 있으므로 공개 저장소에 추가하지 않습니다. 이미지 제거는 익명화가 아닙니다. 제출 파일은 참가자가 별도로 확인해 업로드하며, 이 저장소에는 로그 원문이나 비밀값을 포함하지 않습니다.
