/goal GS2500 해커톤의 데스크톱 웹앱을 완성해줘. GS25 영업관리 매니저가 담당 점포의 전년 동기 대비 매출을 보고 개입할 곳을 고른다. 매장별 진열 후보를 같은 조건의 24시간 3D 실험으로 비교하고, 점주가 납득할 작은 변경안을 승인한다. 점주는 승인된 자기 점포 제안의 현재 진열 사진·선반 이동 도식·추천 이유를 보고 수용·부분 실행·거절을 선택하며, 변경 사진과 선택적 의견만 남긴다. 매니저와 본사는 4주 후 합성된 좋은·부진·미회신 사례를 함께 보고 다음 지원을 판단한다. 3분 발표 경로가 별도 DB 없이 공개 Vercel URL에서 실제 동작해야 한다.

해결할 문제와 사용자: 본사 표준 진열은 참고 지침일 뿐 점포별 취급 상품, 재고, 동선, 수요에 그대로 맞지 않는다. 점주는 매출을 올리고 싶지만 번거로운 일을 근거 없이 추가하고 싶지 않다. 매니저의 핵심 경험은 가맹점 성과 분석, 시뮬레이션 과정·결과, 진열 제안 세 가지다. 진열은 매출 개선 수단 중 하나이며, 맞지 않는 점포에는 발주·행사·현장 지원 등 다른 가설을 남긴다. 본사에는 개별 성공담뿐 아니라 여러 점포의 전년 동기비, 채택률, 점주 부담, 부진 사례를 보여준다.

완료 상태: 현재 `main`에 병합된 유찬님의 `demo/`를 보존하면서 루트의 임시 페이지를 하나의 데스크톱 웹앱으로 바꿔줘. 매니저 홈의 점포별 전년 동기비 → 개입할 매대와 현재 상태·후보 근거 → 여러 점포·여러 옵션의 3D 전광판 → 특정 후보의 24시간 실험 결과·3D 행동 → 매니저 승인과 수정 가능한 점주 안내 문자 초안 → 승인된 안만 보이는 점주 PC 화면 → 현재 매대 사진 한 장에 연결된 위치 표시·선반 단면도·이동할 상품과 이유 → 수용·부분 실행·거절, 사진 파일·의견 접수 → 4주 후 합성 회고를 이어줘. 기존 `demo/`에는 9개 합성 점포 × A/B/C/D 네 후보, 빠른 비교·실시간 관찰, 24시간 실험, 같은 브라우저의 승인·점주 미리보기가 있다. 이 숫자는 현재 데모 설정이지 제품 한계가 아니다. 기존 3D 구현과 테스트를 덮어쓰거나 콘티의 3D 와이어프레임으로 교체하지 마. 스토리보드 HTML은 화면과 발표 흐름의 참고 자료다.

완료 확인 기준: 공개 URL에서 위 경로를 데스크톱 브라우저로 끝까지 클릭할 수 있어야 한다. 미승인안은 점주 화면에 보이지 않고 승인한 점포·매대·후보만 이어진다. 웹앱의 점포·상품·SKU·재고·선반 위치·후보 ID와 3D 실험 및 승인 스냅샷은 하나의 재현 가능한 합성 시나리오에 맞는다. 현재 엔진의 비교 단위는 **24시간**이다. 네 후보에 동일 시드·초기 총재고·잠재 고객 일정을 적용한 실제 계산 결과를 사용하고, 본사 표준안 A를 근거 없이 ‘현재 진열’이라고 부르지 마. 현재 진열 기준선이 별도라면 명확히 모델링하고, 그렇지 않으면 ‘현재 대비 매출 상승’ 수치를 주장하지 마. 후보가 동률·역효과면 그대로 보여주고 억지로 우승안이나 상승률을 만들지 마. 전년 동기비 실적, 24시간 합성 실험, 4주 후 합성 관찰은 서로 다른 지표·시점이다. 30일 결과는 현재 엔진에 없으므로 30일 시뮬레이션으로 표시하지 마. 발표에 꼭 필요하면 별도 가정을 명시한 전망으로만 분리해줘.

점주 경험과 데이터 진실성: 점주가 무엇을 어느 선반으로 옮기라는 것인지 도면만 보고 이해할 수 있어야 하며, 인기·재고·할인·신상품·다른 점포 사례·합성 SNS 신호 중 실제로 준비된 근거만 표시해줘. 신규 발주 권고는 실제 발주가 아니다. 사진 선택은 미리보기와 접수 상태를 제공하되 자동 판독·진열 검증이나 서버 영구 저장으로 표현하지 마. 점주가 화면에서 진열을 편집하게 만들지 말고 실제 현장에서 부분 실행할 자유를 남겨줘. 점주 안내 문자는 수정 가능한 초안이며 실제 발송하지 않는다. 회고는 제안·승인·회신의 분모를 나눠 보여주고 성공·부진·미회신과 다른 설명 가능성을 함께 적어줘. 실제 GS25 데이터·계정·사내 시스템·실시간 SNS 연동, 인과적으로 입증된 매출 상승, 실제 고객 행동 예측을 주장하지 마. 합성 페르소나 1,000개는 실제 GS 고객이 아니며 출처·파생 가정은 `demo/data/PERSONA-SOURCE.md`를 따른다.

제약과 판단 범위: 별도 DB·외부 저장 서비스·실제 문자 발송·실제 발주·모바일 UI는 범위 밖이다. 같은 브라우저 `localStorage`의 데모 승인은 접근 제어나 기기 간 전달이 아니다. 사진의 보존 범위와 새로고침 동작을 UI·README에 정확히 적어줘. 공개 정적 배포의 기본 경로는 로컬 규칙 엔진이며 API 키 없이 작동해야 한다. `demo/server.mjs`의 선택적 JEV 호출은 로컬 Node 서버용이고 키와 인증 서버를 정적 배포에 싣지 마. 키가 없거나 호출 한도가 다해도 핵심 데모가 막히면 안 된다. 모델 실호출, 로컬 규칙, 사전 계산·재생, 합성 회고를 각각 정확히 표시해줘. UI의 세부 표현은 스스로 결정해도 되지만 유료 서비스, 실제 외부 시스템, 실데이터, 삭제, 제품 목표 변경은 먼저 CEO 타오의 승인을 받아줘.

허브 운영과 작업 순서: 이 `/goal`을 입력받은 메인 Codex 작업 하나가 허브다. 우선순위, 독립 작업의 파일 소유권, 동료 3D 코드와 웹앱 연결, 테스트, GitHub·Vercel 업데이트, 제출용 메인 세션 JSONL을 책임져줘. 유찬님의 브랜치는 이미 `main`에 병합되었으므로 다시 병합하지 말고 `demo/README.md`와 코드의 실제 입력·출력·승인 계약부터 확인해줘. 유찬님이 별도 작업에서 후속 3D 변경을 할 수 있으니 기존 파일 소유권을 존중하고 공통 fixture나 어댑터로 결합해줘. 저장소의 사용자 변경과 로컬 비밀 파일은 보존해줘. 가장 작은 ‘성과 확인 → 24시간 후보 비교 → 매니저 승인 → 점주 도면 확인’ 경로를 먼저 완성·검증하고 사진 접수와 회고를 붙여줘. 발표용 3분 경로가 오래 걸리는 계산에 막히면 검증 가능한 엔진 결과의 사전 계산·재생을 명시적으로 사용하고, 진행 중인 실험이나 모델 실호출인 것처럼 꾸미지 마.
